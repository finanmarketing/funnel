## 1. Что это за проект

Полностью автоматический пайплайн маркетинговой воронки eZaem:

```
Яндекс.Метрика Logs API → PostgreSQL → payload.json → HTML-дашборд → письмо
```

Воронка: Трафик → Регистрация → Скоринг → Выдача.
Верхнеуровневая метрика: **FCR = CR × AR × TR**.
Наша часть — **CR** (маркетинг). AR и TR — чужие зоны, см. раздел 9.

Индексы: `ix_metrica_visits_load_date`, `ix_metrica_visits_clientid`,
`ix_metrica_runs_started`, `ix_metrica_runs_stage_status`.

**`DROP SCHEMA` строго запрещён** — схема чужая, в ней боевые объекты.
Схема `public` только на чтение (`public.clients`).

## 5. Решения, которые НЕ переобсуждать

Каждое проверено на данных, а не принято по интуиции.

1. **Мост:** `ym_s_clientid` = `clients.client_number` (**НЕ** `clients.id`, там сдвиг ~100 тыс.).
2. **Дата регистрации:** поле `entity_created`. Колонки `created_at` **не существует**.
3. **Набор полей Метрики: 91.** Зафиксирован в `state/visit_fields.json`.
   Отброшенные 21 поля — e-commerce (`purchase*`, `products*`, `impressions*`),
   на eZaem не размечены, в воронке не участвуют. Проверено: на 02.08 все они пусты,
   при этом все критичные поля и 10 `parsedParamsKey*` заполнены на 100%.
4. **Колонки `ym_s_browser` НЕ существует** — Logs API её отклоняет.
   Разрез «браузер» строится на `ym_s_browserengine`.
5. **`lastTrafficSource='undefined'`** маппится в `'-'` (в шаблоне это «не определён»).
6. **`deviceCategory`** приходит кодами: 1=Десктоп, 2=Смартфон, 3=Планшет, 4=ТВ.
7. **`goalsID`** парсится в SQL через `string_to_array(trim(both '[]' ...), ',')`,
   не через `ast` (в разы быстрее).
8. **Уникальные clientID считает PostgreSQL** через `count(distinct)`, а не
   питоновскими множествами. Это обходит ограничение по памяти (70+ целей × часы
   не помещаются в 4 ГБ) — сервер агрегирует, Python получает готовые числа.
9. **Строгая лесенка** — через `bit_or` битовой маски на стороне БД, длина префикса
   считается на десятке уникальных масок вместо миллиона clientID.
10. **Уровень `hour`** содержит только 17 шагов; события на нём не считаются.
    Следствие: в почасовом разрезе блок «Подробнее» у шага пуст. См. бэклог.
11. **COPY** идёт в формате `FORMAT csv, DELIMITER E'\t', QUOTE E'\x01'`.
    Обычный `FORMAT text` ломается на бэкслешах в referer, CSV с настоящей кавычкой —
    на кавычках внутри URL. `\x01` в данных Метрики не встречается.
12. **Идемпотентность:** `DELETE` дня → `COPY` → `commit`, каждый день отдельной
    транзакцией. Повторный запуск безопасен.
13. **Скользящее окно** `RELOAD_WINDOW_DAYS=3` — каждый прогон переливает вчера,
    позавчера и D-3. Данные Метрики за текущие сутки не грузим никогда.
14. **Пароли в `.env` — только в ОДИНАРНЫХ кавычках.** Спецсимволы `#`, `^`, `%`
    ломают три парсера: dotenv (комментарий), libpq (conninfo), cmd (экранирование).
    Подключение к PG идёт именованными аргументами `psycopg2.connect(host=..., ...)`,
    а не строкой DSN — тогда пароль передаётся байт в байт без парсинга.
15. **Автозапуск отключён** (задача `FunnelEzaemDaily` удалена). Корпоративный VPN
    требует подтверждения с телефона (MFA) — полная автономность на ноутбуке
    недостижима технически.

## 7. Как работает оркестратор

`run_pipeline.py` выполняет 5 этапов строго последовательно, стоп при первой ошибке:

1. `sync_goals` — справочник целей из Management API (~60 с)
2. `ingest_metrica` — загрузка визитов через Logs API (~940 с)
3. `build_payload` — расчёт всех уровней и разрезов (~520 с)
4. `render_dashboard` — подстановка данных в шаблон (~4 с)
5. `deliver` — письмо с вложением (~20 с)

**Защиты:**
- Перед каждым этапом — TCP-проверка `10.174.17.38:5432`. Сети нет → ждём до
  `NET_WAIT_SECONDS`, проверяя раз в 30 с. Проверено: VPN подняли — через 30 с продолжил.
- Этап упал → ждём сеть → повторяем, до `STAGE_ATTEMPTS` попыток.
- Записи со статусом `start` старше `STALE_RUN_HOURS` помечаются `orphaned`.
- Логи по прогонам `logs/run_YYYY-MM-DD_HHMMSS.log`, автоочистка старше `LOG_KEEP_DAYS`.
- При падении — письмо **только на `ALERT_TO`** с классифицированной причиной
  и подсказкой, что делать.

**Устойчивость Logs API:**
- Перед созданием заказа ищется живой заказ на тот же период — переиспользуется.
- Мёртвые заказы (`processing_failed`, `canceled`) чистятся автоматически.
- Опрос статуса переживает до 10 подряд сетевых сбоев (заказ на стороне Метрики жив).
- Ручная уборка: `python pipeline\ingest_metrica.py --cleanup`

## 11. Грабли (нарушение = потерянные часы)

1. **Cursor обрывает длинные вставки.** `build_payload.py` вставился на 276 строк
   без хвоста — синтаксис валидный, скрипт молча ничего не делал. После создания
   любого файла проверять: `(Get-Item путь).Length` и наличие `__main__`.
2. **PowerShell:** запуск команды, начинающейся с кавычки, требует `&` (call operator).
   Проще использовать `python script.py` — интерпретатор в PATH.
3. **DBeaver:** `Ctrl+Enter` выполняет один оператор под курсором, а не скрипт.
   Пустая строка разрывает выполнение. Миграции применять через `apply_sql.py`.
4. **DBeaver режет вывод до 200 строк** — при ручных сверках отключать лимит.
5. **Parts > 0 в Logs API повторяют шапку** — пропускать первую строку.
6. **`load_dotenv()` ищет `.env` от текущей директории** — запускать из корня
   либо использовать абсолютные пути от `__file__` (так сделано в v1.2).
7. **Задача в планировщике не наследует окружение Cursor** — в `/TR` нужен
   абсолютный путь к тому же `python.exe`.
8. **Для QlikView-скриптов НЕ использовать CTE** — только вложенные подзапросы.

## 12. Правила работы с Claude

- Файлы создавать **командой в терминал**, затем вставлять **код целиком**,
  не фрагментами.
- После создания файла — проверять размер.
- Никаких DDL/DML в схеме `public`.
- В DBeaver под computer use — **только read-only подключение** (учётку запросить
  у Влада Болдырева).
- Каждое утверждение о данных проверять на строках, а не выводить логически.
- Общение по-русски, код и комментарии в коде — по-английски.
